# x402 v2 operations

Paygrid charges HTTP APIs and pays authorized HTTP APIs through one backend executor.
MCP tools themselves keep their existing authentication; this release does not sell MCP calls.
Payments are direct to the API seller and do not traverse PaygridRouterV2 or collect its fee.

## Default policy

| Asset | GET /api/x402/data | Max outgoing payment | Daily outgoing budget |
| --- | --- | --- | --- |
| USDC | 0.10 | 5 | 50 |
| USDT | 0.10 | 5 | 50 |
| wMXN | 2 | 100 | 1000 |

Each currency is independent. Budgets use UTC days and are shared by wallet and network across MCP and CLI.
No FX, swaps or assumed dollar value for wMXN. Configuration values are atomic decimal strings.
Outstanding reservations remain counted across midnight until confirmed or proven unused after expiry. Confirmed spend is charged to its first confirmation day in UTC; recovering content never changes that day.
The default merchant policy permits only GET on the configured public API's /api/x402/data and its configured receiving address.
Additional merchants require exact HTTPS origin, path, method and recipient allowlists in X402_MERCHANTS.

## Local secrets and setup

Run from backend:

```sh
npm ci --omit=peer
npm run x402:setup
```

Setup creates backend/.env.x402, backend/.env.x402.worker and client credentials in mcp/.env.x402 and agent/.env.x402, all mode 0600 and ignored by Git.
It refuses to replace existing keys. The payer key exists only in backend/.env.x402; the worker receives only public payer identity, facilitator credentials and the audit encryption key.
Both feature flags start false.

Create the facilitator API key manually at https://x402.celo.org and put X402_API_KEY in the backend and worker files.
Verify X402_PAY_TO, fund the dedicated payer and ensure facilitator credits are available.
Do not reuse administrative, treasury or claim-signing keys. Never paste secrets into chat.
Keep X402_ENCRYPTION_KEY unchanged while recoverable operations exist.

Apply migration 20261124000016_x402_payments.sql using the repository migration runner.
Use a separate Supabase test project and matching backend environment when running the Sepolia canary. The operator chose to prioritize a mainnet smoke test on 2026-11-25; real Sepolia validation remains unexecuted.

Readiness does not prove metered settlement credentials or remaining credits; the real canary does.
Facilitator pricing is read from its /api/config; its charges are separate from payer token budgets.

## HTTP API

- GET /api/x402/capabilities: public live readiness, network, enabled assets and prices.
- GET /api/x402/data: public paid reference resource. No query parameters. Returns 402 + PAYMENT-REQUIRED, then accepts PAYMENT-SIGNATURE and returns PAYMENT-RESPONSE after settlement and onchain transfer checks.
- POST /api/x402/pay: operator service credential via Authorization: Bearer X402_EXECUTOR_API_KEY. Requires Idempotency-Key (16–128 letters, digits, underscores or hyphens).
- GET /api/x402/payments/:operationId: same executor credential; inspect pending/unknown payments without creating another operation.

Outgoing JSON:

```json
{
  "url": "https://api.celopaygrid.xyz/api/x402/data",
  "method": "GET",
  "preferredToken": "wMXN"
}
```

POST requests may include body. GET bodies, custom payment headers, keys and policy overrides are rejected.
The executor does not forward its service credential to merchants.
Requests are limited to 64 KiB, merchant responses to 1 MiB, paid authorization validity to 120 seconds.
X402_SELLER_ALLOWED_PAYERS optionally restricts new incoming payments to comma-separated wallet addresses during a canary. Empty accepts public payers. Previously accepted authorizations retain result/receipt recovery when this policy changes. Capabilities expose sellerRestricted without publishing its address list. While restricted, MCP metadata keeps x402Support=false; the authenticated canary tools remain usable.
DNS answers are checked and pinned to public addresses; redirects, private targets, metadata endpoints and non-HTTPS targets are blocked.

Outgoing results include operationId, state, paid, a sanitized payment summary, result and error.
HTTP 202 means pending or unknown, not a new payment challenge.
A settled operation may contain RESOURCE_DELIVERY_PENDING or RESOURCE_DELIVERY_FAILED: the transfer happened; do not pay again. The worker recovers interrupted content for up to 24 hours while its confirmed spend counts against the daily budget.
Identical retries return the same operation. Changing the request under the same key returns 409.
The old x-paygrid-x402-proof and caller-provided transaction hashes never authorize access.

## Recovery and retained evidence

The database reserves budget and the wallet execution slot before signing.
Signed authorizations are encrypted with AES-256-GCM and committed before any paid request is sent.
The ledger permanently deduplicates authorization nonces and request identities.
Do not place signed headers or ciphertext in logs, monitoring or client responses.

A lost response keeps the operation unknown and retains its budget.
The worker retries only the stored authorization, never creating another signature or accepting changed terms.
It confirms receipts against successful chain transactions, the exact payer/token/recipient/amount transfer and the authorization nonce. Permit2 requires the standard direct x402 proxy settlement call. A transaction hash cannot back two operations in the same direction.
Expired authorizations release reservations only after the chain proves the nonce is unused.
A used nonce without a recoverable receipt stays unknown for operator investigation.
A token transfer cannot be inferred from a nonce being consumed.

Resource results expire after 24 hours; authorization identifiers remain.
An expired result returns 410 for the original paid request, never another charge.

X402_CANARY_TOKENS=USDC selects only USDC without attempting unfunded currencies. Omit it to validate all enabled currencies. The final report lists only currencies actually validated.

## Deploy and rollback

Build backend, mcp-http and x402-worker with docker-compose.prod.yml.
The TypeScript build stage sets a 1536 MiB V8 heap limit so 1 GiB VPS hosts with swap can compile it. This limit applies only to the build command. Build backend and MCP sequentially on those hosts:

```sh
docker compose -f docker-compose.prod.yml build backend &&
docker compose -f docker-compose.prod.yml build mcp-http
```

For larger build hosts, the limit can be overridden with `docker compose -f docker-compose.prod.yml build --build-arg NODE_BUILD_HEAP_MB=2048 backend`.

With both flags still false, run the no-payment preflight against the deployment environment:

```sh
docker compose -f docker-compose.prod.yml run --rm --no-deps backend node dist/x402-preflight.js
```

It validates the proposed enabled configuration in memory and does not change the feature flags.
The worker has no public port and receives no payer private key.
Nginx must allow MCP-Protocol-Version and both JSON/SSE Accept types, disable proxy buffering and use a 180-second upstream read timeout.
Responses and payment challenges must not be cached by proxies.

Monitor x402 operation states, reserved budgets, unknown age, facilitator credit failures and chain/receipt mismatches.
The ledger is service-role only. Inspect state/error/receipt fields; never export ciphertext.
An unknown payment requires reconciliation, not manually resetting its budget or issuing another intent.

For rollback disable X402_SELLER_ENABLED and X402_PAYER_ENABLED on the backend.
Keep the worker, ledger, credentials and encryption key available for already signed operations.
Disabling the payer stops new signatures; authorizations already issued can remain valid until expiry.
Never deploy the removed legacy proof implementation as a fallback.

### Concurrent replay check

`mcp/src/x402-replay-check.js` audits already settled MCP canaries. It validates
all original keys against SHA-256 fingerprints derived from the ledger, plus
network, resource, operation IDs and hashes, before starting any client. It never
generates an idempotency key. Execution launches three existing MCP canary
clients in parallel per token, processes tokens sequentially, and requires the
same receipts and HTTP 200 results. It revalidates the evidence afterward.

Run from the VPS repository after updating this branch; the script can be passed
to the existing container without rebuilding its image:

```sh
# Read-only evidence validation; no clients or payment calls are started.
docker compose -f docker-compose.prod.yml exec -T mcp-http node --input-type=module - < mcp/src/x402-replay-check.js
# Only after that passes: concurrent reuse of the same settled operations.
docker compose -f docker-compose.prod.yml exec -T mcp-http node --input-type=module - --execute < mcp/src/x402-replay-check.js
```

This checks concurrent recovery of completed payments. It does not exercise the
race to sign a fresh operation, a backend/worker crash during uncertain settlement,
or wMXN client interruption. Those live cases and real Sepolia USDC remain
unexecuted. Local tests reject changed keys, missing/duplicate evidence and
changed receipts before subsequent token groups can run. The local MCP credential
was rejected by production during a status read; execute authenticated replay
checks with the existing credentials inside the VPS container, without copying
credentials into chat.
